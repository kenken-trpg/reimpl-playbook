# 方法

既存のプログラムを別のフレームワークで作り直す案件に共通する段取り。
`chummer-web`（C# WinForms のデスクトップアプリ → Python + TypeScript の Web アプリ）
で実際に効いたものだけを残してある。

## 前提：仕様書は存在しない

リプレース対象に仕様書があることはまずない。あっても現物と食い違っている。
**動いている実装そのものが仕様**であり、その実装が書き出したファイルが唯一の証言になる。

ここから 3 つの帰結が出る。

1. **正解は自分で用意しない。** 「このキャラクターの合計は 3300 のはず」と手で書いた
   期待値は、自分の理解のコピーでしかない。本家が自分で書き残した数字を使う。
2. **現物を大量に集める。** 1 件の往復よりも 34 件の突き合わせのほうが情報量が多い。
   本家のテスト用データがあれば最優先で取り込む（[01](01-oracle.md)）。
3. **対象はこちらの都合で動かない。** 上流は勝手に変わる。ピン留めして、
   上げるときは意識的に上げる（[02](02-upstream-pin.md)）。

## 順序

着手順にはかなり強い正解がある。逆にすると数か月戻る。

| # | やること | なぜその順番か |
|---|---|---|
| 1 | **読み込み** — 本家のファイルを自分の状態に | これがないと何も測れない |
| 2 | **突き合わせ（balance）** — 本家が書いた合計と自分の計算 | 対応表も規則の知識も要らずに「どこかが違う」が出る |
| 3 | **書き出し + 往復（roundtrip）** | 自分の import が落としているものが出る |
| 4 | **忠実性（fidelity）** — 本家に読ませられるか | 往復では原理的に見えない欠落が出る |
| 5 | **カバレッジ** — 本家の語彙のどこまで実装したか | 残りの作業量が初めて数字になる |

2 を飛ばして 5 から始めたくなるが、順序が逆。カバレッジは「何を作るか」の地図で、
突き合わせは「作ったものが合っているか」の計測であり、後者がないまま前者を進めると
**実装済みで間違っている**項目が積み上がる。これが一番高くつく。

## 赤いままでよいもの、緑でなければならないもの

- **balance は赤くてよい。** 最初はほぼ全件ずれる。数か月かけて下げていく読み物であって、
  CI で落とすものではない。落とすようにすると「常に赤い CI」になり、誰も見なくなる。
- **fidelity と roundtrip は緑でなければならない。** どちらも最初から緑にできる
  （対象フィールドを絞ればよい）。緑で始まり緑を保つものだけが門になれる。

この非対称が `tools/oracle/cli.py --gate` の挙動そのもの。

## 「わざと違う」を置く場所を先に作る

どの検査にも必ず「本家と違うが、それでよい」項目が出る。
置き場所がないと、検査はいずれ次のどちらかになる：
全部赤くて誰も見ない、か、空の実装で黙らせたもの。

だから最初から **理由つきの例外表**を用意する（`ACCEPTED_DROPS`、`SILENT`）。
1 行と 1 文で書ける程度に安く、何も書かずには済まない程度に高い、という値段設定にする。

## 散文と計画の分離

やったことの計画書（`docs/plans/`）と、今どうなっているかの説明（`docs/` 直下）は
**別物**で、混ぜると両方死ぬ。[03](03-docs-and-plans.md) を参照。
