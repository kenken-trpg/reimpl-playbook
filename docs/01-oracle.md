# 01 本家を正解として測る

実装：`tools/oracle/`、配線例：`example/adapter.py`、テスト：`tests/test_oracle.py`

```
python -m tools.oracle.cli --adapter your.adapter --corpus vendor/upstream-corpus
```

## コーパス：本家のテストデータを取りに行く

本家に `Tests/TestFiles/` のようなディレクトリがあれば、それが最良のコーパス。
作者が「これは読めなければならない」と考えた現物であり、端のケースが入っている。

**データ本体と同じ ref から取る。** 突き合わせの材料と計算の材料が別の時点だと、
出た差が「実装の差」なのか「版の差」なのか永遠に決着しない。
`tools/pin/fetch_upstream.py --corpus` がこれをやる。

本家にテストデータがない場合は、自分で本家を動かして書き出す。
手で期待値を書くのだけは避ける（[00](00-method.md) の前提）。

## 3 つの検査が答えている別々の問い

### balance — 本家が書き残した合計

本家が計算結果そのものを書いているフィールドを探す。
残り予算、合計金額、総ポイント。これが見つかれば、
**対応表も規則の知識もなしに「どこかが違う」が出る**。最初に作るべきはこれ。

- `is_comparable()` が要る。下書き・途中状態・別モード（その数字が「残り」ではなく
  「累計」になるなど）を比較すると、欠陥でない差が並んで報告が読まれなくなる。
- 許容差（`TOLERANCES`）は書式が許す限り狭く。広げるときは理由を書く。
- 例外で止めない。コーパス全体を回すと必ず読めない現物があり、
  そこで止まる台は 1 回につき 1 件しか報告できない。

### roundtrip — 書き出して読み直す

安いわりに実在のバグを捕まえる：**import は読むのに export に書く場所がない**項目。

原理的な盲点がある。**どちらも読んでいないフィールドは、
誰も見ていないので変わらずに戻ってきて、往復は合格と言う。** これが次の検査の存在理由。

保持物（`holdings`）だけでなく**計算結果も**比較すること。
行は揃っているのに rating やフラグが落ちて答えが変わる、という往復がある。

### fidelity — 本家に読ませられるか

書き出したファイルを、**本家の目**で原本と突き合わせる。
本家がそのファイルのもう一人の読者であり、本家が何を期待するかの唯一の記述は
本家自身が書いたファイルだから。

設計上の非対称：

- 両方が書いていて文字列が違う → **失敗**
- 原本にあって書き出しにない → **失敗**（例外表にあれば報告のみ）
- まだ考えていないもの → **失敗**

考えていないものが落ちるからこそ、実装が育っても表が正直でいられる。
例外は 1 行と理由 1 文（`ACCEPTED_DROPS`）。理由に「問題ない」と書かれたら、
それは理由ではない。

比較対象（`COMPARE`）は、現物の**ヘッダ**に絞るのが実用的。
一覧部分は自分のカタログから組み直すので、違って当然。

## Oracle は計算してはいけない

`Oracle` は本家の出力を**読むだけ**。
ここで計算を始めた瞬間、比較はハーネス同士の照合になり、
間違った理由で subject と一致するようになる。これは気づけない。

## 報告は 1 件 1 行、最後に件数

表が成果物。週に一度は人間が目を通すものだから、
1 現物 1 行、情報量の多い列を左に、最後に「今日は何件合っているか」。
覚えられる数字はこれだけ。
