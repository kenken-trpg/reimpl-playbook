# 02 上流データのピン留め

実装：`tools/pin/fetch_upstream.py`

## 本家のデータをリポジトリに入れない

2 つ理由がある。

1. **ライセンス。** 本家のデータは大抵、自分のリポジトリに複製すると
   そのリポジトリ全体のライセンスに影響する種類のもの。
   setup 時に取得すれば、ツリーは自分のコードだけで済む（`vendor/` は gitignore）。
2. **再現性。** subject は本家のスキーマを解析している。そのスキーマは本家の
   デフォルトブランチで予告なく変わる。ピンがあれば
   「一晩でテストが壊れた」が「誰かがピンを上げた」になる。

## ピンの上げ方は手順である

ピンを上げるのは意識的な行為で、必ずこの順でやる：

1. `--ref <sha>` で取り直す
2. 全テスト + 型検査
3. **oracle ハーネスも回す**（差分が balance に出る）
4. 必要になったパーサ修正と**同じコミット**で新しい SHA を入れる

とくに：**自分が上流に送った修正がマージされても、こちらのコードには届かない。**
届かせるのはこの手順であって、マージではない。
上流で名前が変わる種類の修正だと、それ自体が突き合わせの一致/不一致を動かす。

## CI キャッシュの鍵はスクリプトのハッシュ

ref だけを鍵にすると、`FILES` にファイルを足したときにキャッシュが当たってしまい、
足したファイルが降ってこない。**このスクリプト自身のハッシュ**を鍵にすれば両方で外れる。

## ディレクトリ一覧は API、本体は raw

ファイルの取得（raw.githubusercontent）にレート制限はないが、
ディレクトリの一覧は API 呼び出しで、未認証だと **IP あたり 1 時間 60 回**。
共有 CI ランナーではジョブが始まる前に使い切っていることがある
（`HTTP Error 403: rate limit exceeded`）。
Actions の `GITHUB_TOKEN` を渡せば 5,000 回になる。
