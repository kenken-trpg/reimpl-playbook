# 03 ドキュメントと計画

雛形：`templates/docs/`

## 現状説明は 4 点セットで足りる

リプレース案件の `docs/` 直下は、この 4 つ以上にはならない。

| ファイル | 答える問い | 肝 |
|---|---|---|
| `architecture.md` | 全体の形とデータの流れ | **1 文で言う**節を先頭に置く。図は ASCII 1 枚 |
| `adding-rules.md` | 機能を 1 つ足す手順 | レシピ形式。**各レシピがテストで終わる** |
| `data-pipeline.md` | 本家のデータがどう入ってくるか | 取得 → 解析 → 整形の 3 段、各段の不変条件 |
| `deploy.md` | 動かすまで | 一度きりの作業と毎回の作業を分ける |

`adding-rules.md` の価値は「書いてある」ことではなく、
**レシピの最後が必ずテストになっている**こと。
リプレースでは似た作業が何百回も繰り返されるので、
手順が 1 か所にあるかどうかが速度に直結する。

## plans は「記録」であって「説明」ではない

`docs/plans/` に実施した作業計画を置くなら、README の先頭にこう書く：

> ここにあるのは**実施済みの作業計画**です。書かれた時点のコードを前提にしているので、
> 現状の説明としては読まないでください。「なぜこの形になっているか」を辿るための記録です。

これがないと 2 つとも死ぬ。古い計画が現状説明として読まれて誤解を生み、
それを避けようと計画を書き換え続けて記録としての価値が消える。
**書いた時点で凍結する**と決めてしまえば、両方とも使える。

計画を分類して一覧にしておく（アーキテクチャ / データ / エンジン / テスト / デプロイ）。
リプレースは分割リファクタリングの連続になるので、この一覧自体が
「どこをどう切ったか」の履歴になる。

## 計画書の型

1 本 100〜300 行。中身は：

1. **いま何が問題か** — 行数、重複、型が付かない箇所など、測れる形で
2. **到達したい形** — ファイル構成を具体的に
3. **段取り** — 1 PR 単位に割る。各段が単独でマージできること
4. **やらないこと** — ここが一番効く

「やらないこと」を書いておくと、半年後に同じ提案が出たときに即座に片付く。
