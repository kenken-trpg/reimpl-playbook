# 07 運用

実装：`tools/ops/`

リプレース案件は**小さな PR が異常に多くなる**。
規則を 1 つ、項目を 1 つ、タブを 1 つ。ここの摩擦はそのまま速度になる。

## changelog は断片で書く（`changelog.py`）

全 PR が `## [Unreleased]` の直下を編集していたので、
同時に開いている 2 本は必ず 2 本目が衝突した。

断片方式：PR は `changelog.d/<name>.<type>.md` という**誰も触らないファイル**を足し、
リリース時に `collect` が `[Unreleased]` に畳む。衝突は構造的に起きない。

- `check-pr` が CI で「コードを変えたのに断片がない」を落とす
- ただし bot の依存更新は、**出荷しない**マニフェストだけが動いた場合は免除。
  出荷する側（`dependencies`）が 1 バイトでも動いていたら要求する。
  パッチ更新ごとの箇条書きは誰も読まないが、
  イメージが抱えている依存のセキュリティ修正は利用者に影響する。
- どうしても不要なら PR タイトルに `[skip changelog]`

## 順次マージ（`merge_chain.sh`）

PR を 1 本ずつ rebase → 検査 → push → 全チェック緑を確認 → auto-merge、
マージを待ってから次へ。デフォルトブランチが strict 保護だと手でやるのは無理。

落とし穴が 3 つ、全部実際に踏んだ：

1. **先に auto-merge を武装したまま渡さない。** 武装済みの PR が勝手にマージして
   デフォルトブランチを動かすと、いま rebase した PR が BEHIND に取り残される。
   マージはこのスクリプトからだけ起こす。
2. **auto-merge を渡す前に全チェックを見る。** 保護が *required* と呼ぶものだけを
   GitHub は待つ。必須でないジョブが赤いまま merge した事故がある。
3. **両側の差分を見て検査範囲を決める。** 「ブランチが何を変えたか」だけでは不足。
   デフォルトブランチがその下で動いている。

衝突の自動解決（`keep_both_sides.py`）は、
**両方が追記しただけ**の場所に限る。changelog 断片とテスト。
翻訳辞書は追記に見えて駄目——語の衝突は選択であり、重複キーは実行時にしか出ない。

## doctor（`doctor.sh`）

リプレース案件は setup が異常に長い（処理系 + フロントのツールチェーン +
コンテナ + 本家データの正しい ref）。壊れ方が全部違う。
これがないと新規参入者が最初に見るのは 3 層下のテストエラーになる。

**非致命的に、1 回で全部出す。** 終了コードは CI のためで、読む人のためではない。

## retry（`retry.sh`）

依存のインストール限定。PyPI も npm レジストリも可用性は保証されていない。
一瞬空のインデックスを返したとき、pip はそれを**本物の間違いと同じ形**で報告する：

```
ERROR: Could not find a version that satisfies the requirement ... (from versions: none)
```

`from versions: none` が目印。「ピンが満たせない」ではなく「インデックスが何も返さなかった」。
ピンを強くしても防げないので、**もう一度訊く**。間を空けるのが要点（15 秒、次に 60 秒）。
