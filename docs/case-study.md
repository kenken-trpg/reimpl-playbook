# 事例

この playbook の出どころ。抽象化した記述だけだと
「自分の案件は違う」で終わるので、一つの案件で実際に起きたことを残しておく。
固有名と業務の中身は落とし、形だけ書いてある。

## 何から何へ

- **本家**：C# / WinForms のデスクトップアプリ。規則の多い計算ツールで、
  規則そのものは数十本の XML データファイルに入っている。
  独自形式の保存ファイルを書き出し、読み込む。
- **subject**：Python（API）+ TypeScript（SPA）の Web アプリ。
  状態はブラウザが持ち、計算はステートレスなバックエンドが返す。

**フレームワークも基本設計も違うので、コードは 1 行も共有できない。**
共有できたのはデータの解釈と、ファイル形式と、規則の理解だけだった。

規模の目安：本家のデータ XML 約 30 本、本家が同梱していたテスト用保存ファイル
数十件、subject 側のテスト千件規模。

## 効いたもの

| 仕組み | 具体的に何が出たか |
|---|---|
| 突き合わせ | 本家が「残り予算」として書き残した数字との差が、品目別の値段ずれまで切り分けられた。手では絶対に見つからない桁の差 |
| 往復一致 | 全件一致を維持。import は読むのに export に書く場所がない項目を、都度検出 |
| fidelity | **本家の実行ファイルが書き出しを読めるか**の門。CI ジョブとして常時緑 |
| ピン留め | 上流のデフォルトブランチでのスキーマ変更で一晩で壊れる、を構造的に防止 |
| カバレッジ導出 | 未実装タグを手で数えようとして誤検出した（データ中のタグ文字列を照合する方法では駄目で、ハンドラ表から導出した数字だけが正しかった） |
| changelog 断片 | 並行 PR の changelog 衝突が消えた |

## 予想外だったこと

- **本家のデータのバグがこちらで見つかる。** 本家のデータ全ファイルを
  千件規模のテストで解析しているサードパーティ実装は他になかったので、
  文字化け・ID 重複・翻訳漏れが落ちてきた。上流に修正を送っている。
  リプレース側が上流に返せるのは**コードではなくデータ**、というのは一般化できる。
- **「わざと違う」の判断が作業の本体になる。** 本家が書いて二度と読まないフィールド、
  保存された価格と現在の価格表の差、モードによって同じフィールドの意味が変わる
  （「残り」か「累計」か）。検査を作る時間より、例外に理由を書く時間のほうが長かった。
- **突き合わせ結果の多くは直さない。** ある品目カテゴリの金額ずれは、
  保存ファイルに入っている値だけでは直らず、直そうとすると他の現物が悪化すると分かった。
  そこで**理由を書いて放置する**と決め、その判断をスクリプトの docstring に残した。
  次に読む人が同じ午後を使わないように書くのが、この種の結論の唯一の保存方法。
